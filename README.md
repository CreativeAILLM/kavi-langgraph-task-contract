# LangGraph Task Contract: KAVI Task Contract v1 as a state graph

A small, real LangGraph reference implementation of the KAVI Task Contract v1
flow used by the three agent system (Legend, ChatGPT, Hermes). It exists as
engineering evidence and as a testable model of the contract: a task is only
COMPLETED_VERIFIED when its output is checked against its own
DEFINITION_OF_DONE, anything else lands in the ledger as BLOCKED with a
reason, and decision work never executes, it terminates as DECISION_NEEDED.

No network calls, no LLM, no credentials. The execute node is a deterministic
stub so the graph behaviour is fully reproducible and unit testable.

## Run it

```bash
pip install --user --break-system-packages langgraph langchain-core pytest
python3 run_demo.py        # runs 3 sample tasks, prints the ledger
python3 -m pytest          # 7 tests
```

## Graph shape

```
START -> intake -> route --(lane = decision)--> decision_needed -> END
                      |
                      +--(any other lane)--> execute -> verify
                                                            |
                                        (pass or fail, conditional edge)
                                                            v
                                                      ledger_append -> END
```

## Node by node, mapped to the KAVI Task Contract v1

| Node | What it does | Contract mapping |
| --- | --- | --- |
| `intake` | Validates the raw task dict: TASK_ID, OWNER, OBJECTIVE and DEFINITION_OF_DONE keys must be present; TASK_ID, OBJECTIVE and DEFINITION_OF_DONE must be non blank; a preset OWNER must be a known agent. Invalid contracts raise and never enter the graph. | The contract's required fields (TASK_ID, OWNER, OBJECTIVE, DEFINITION_OF_DONE). OWNER may be blank at intake because the next node assigns it, the same way a requested task arrives before ownership is settled. |
| `route` | Picks the single accountable owner from the task's `lane` field: ops, ecommerce and video go to Legend; career, strategy and sales go to ChatGPT; runtime, engineering and infra go to Hermes. The `decision` lane returns no owner. | The ratified ownership map and the one task, one owner rule. A conditional edge sends the decision lane straight to the terminal decision node. |
| `decision_needed` | Appends a DECISION_NEEDED record to the ledger and ends. The task is never executed. | The DECISION_NEEDED status added to the status model: decision topic surfaces to Onur instead of being worked or silently dropped. |
| `execute` | Deterministic stub: builds an output string from the owner, the objective and the task's `deliverable` text. Stand in for the owning agent doing the real work through its own tools. | The OWNER carrying out OBJECTIVE within its lane. In production this is the only node that changes per agent; the contract around it stays the same. |
| `verify` | Extracts checkable keywords from DEFINITION_OF_DONE (tokens of 4+ characters, stopwords removed) and passes only if every keyword appears in the output. Returns the missing keywords on failure. | The evidence rule: COMPLETED_VERIFIED requires evidence checked against DEFINITION_OF_DONE. A bare "done" claim never passes, because the claim words themselves are not the deliverable. |
| `ledger_append` | Appends one JSON record to the local `ledger.json`: COMPLETED_VERIFIED on verify pass, BLOCKED with the missing keyword reason on verify fail. | The shared ledger discipline: every terminal state is written down with owner, objective, output and status, in the same spirit as ops/shared-ledger.json in the kavi-shared-state repo (this local file is a model, not that ledger). |

## Files

- `task_contract/contract.py`: pure contract logic (validation, lane routing
  rule, stub execution, keyword verification). No I/O, independently testable.
- `task_contract/graph.py`: LangGraph wiring, the ledger append/read helpers,
  and `run_task` for one-shot execution.
- `run_demo.py`: three sample tasks (one pass, one verify fail, one
  decision), resets `ledger.json`, prints the resulting ledger.
- `tests/test_graph.py`: intake validation, routing rule, verify logic, and
  end to end runs for the pass, blocked and decision paths.
- `ledger.json`: generated by the demo.

## Deliberate simplifications

- Keyword verification is a model of the evidence check, not the real thing:
  production verification reads the actual deliverable (commit, file, live
  page), here it reads the stub output string.
- The ledger is a local JSON file, not the GitHub shared ledger. Nothing in
  this project reads, writes or pushes to any remote.
- State is a plain TypedDict; no checkpointer or persistence beyond the
  ledger file, because a single task run is short and stateless by design.
